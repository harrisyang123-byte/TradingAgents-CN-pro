## Context

TG-CN 已有 Tier 1 单标的分析引擎（4 分析师 → 投资辩论 → 交易员 → 风险辩论 → Portfolio Manager），基于 LangGraph 实现。分析报告存档在 MongoDB `analysis_results` 集合。

portfolio-advisor 变更（前置依赖）提供持仓 CRUD（Position + PortfolioAccount），支持股票/基金/ETF/黄金/债券多品种。

本设计构建 Tier 2 组合顾问引擎——读存档报告 + 持仓数据 → 三角色辩论 → 输出组合级操作建议。

## Goals / Non-Goals

**Goals:**
- 构建 Tier 2 LangGraph 图，复用 Tier 1 辩论基础设施（StateGraph + 轮转条件边 + DebateState）
- 3 角色各自看不同数据（信息差驱动真正的思维多样性），非相同数据不同人设
- 输出结构化处方（AdviceItem 列表）+ 完整辩论记录
- 异步执行，WebSocket 通知前端
- 多品种兼容（instrument_type 字段区分）

**Non-Goals:**
- 不修改 Tier 1 分析引擎
- 不做对话式追问（Tier 3 规划）
- 不做定时/自动触发（用户手动）
- 不做 Tier 1 的基金/黄金分析支持（只做 Tier 2 层面的兼容）
- 不做交易执行（只给建议）

## Decisions

### D1: Tier 2 图结构 — 复用 vs 新建

**选择**：新建独立的 `AdvisorGraph`，但复用 Tier 1 的辩论模式（DebateState 结构 + 轮转条件逻辑）。

**理由**：Tier 1 和 Tier 2 的图拓扑完全不同——Tier 1 是"分析师→辩论→裁判→辩论→裁判"双层结构，Tier 2 是"三角色独立→三角色辩论→裁判"单层结构。强行复用 Tier 1 的图会导致大量条件分支。复用的是**模式**（DebateState TypedDict、轮转判断函数），不是图本身。

**替代方案**：直接用 LLM Chain 而非 LangGraph → 放弃了流式进度反馈和节点级计时，与 Tier 1 架构不一致。

### D2: 三角色的数据隔离

**选择**：三角色在独立分析阶段看不同的数据子集。

| 角色 | 读取的数据 | 不读的数据 |
|------|-----------|-----------|
| 持仓分析师 | 每只持仓的 Tier 1 报告摘要 + 当前价格 + 持仓成本 | 宏观环境、行业趋势 |
| 策略师 | 组合仓位分布 + 行业集中度 + 各持仓相关性 | 个股报告细节 |
| 侦察兵 | 策略师输出的组合缺口 + 非持仓股票的存档报告 + AKShare 行业数据 | 个股持仓细节 |

**理由**：同一个 LLM 用不同 prompt 不会产生真正的思维多样性。信息差是多 Agent 系统中创造有效分歧的核心机制。

### D3: 侦察兵的数据源

**选择**：三层优先级。

1. 用户历史分析过但未持有的标的（`analysis_results` 中有报告，`positions` 中无持仓），且评级为 Buy/Overweight
2. 策略师识别的组合缺口方向，从 AKShare `stock_board_industry_name_ths()` 获取对应行业成分股
3. 雪球热门 `stock_hot_tweet_xq("最热门")`

**理由**：优先复用已有数据（成本为零），其次用已验证的 AKShare 接口，最后用热度信号。侦察兵只筛选推荐，不做深度分析。

### D4: CIO 裁判的思维约束

**选择**：prompt 中硬编码两项芒格思维工具 + 两项定量红线。

芒格思维：
- 逆向思维：每条加仓/建仓建议必须回答"如果错了最大亏损多少"
- 认知偏差检测：检查禀赋效应、近因偏差、锚定效应

定量红线：
- 单只标的仓位不超过 30%（可配置）
- 单一行业不超过 50%（可配置）

**理由**：思维工具是结构性约束（强制 LLM 走特定推理路径），不是装饰性 persona。定量红线是硬限制，CIO 要么遵守要么在理由中显式说明为何突破。

### D5: 报告时效性

**选择**：默认 7 天过期阈值，存储在 `default_config.py` 中可配置。

**理由**：A 股一周内的分析报告通常仍有参考价值（周频交易视角）。过期不等于不可用——分析师仍引用报告，但标注过期提醒用户重新分析。

### D6: 异步执行模式

**选择**：复用 Tier 1 的异步执行模式——`ThreadPoolExecutor` + Redis 进度 + WebSocket 通知。

**理由**：Tier 1 的 `simple_analysis_service.py` 已有成熟的异步执行、进度回调、WebSocket 通知管线。Tier 2 可复用同一模式，只是进度节点名不同。

### D7: 前端展示方式

**选择**：`el-drawer` 侧边抽屉，不新建页面。

**理由**：组合建议是持仓页面的附属功能，不是独立场景。抽屉可覆盖展示处方（Layer 1）+ 折叠辩论记录（Layer 2），用户可随时关闭回到持仓页面。

## Risks / Trade-offs

**[R1] LLM 调用成本**：3 角色独立分析（3 次）+ N 轮辩论（N×3 次）+ CIO 裁判（1 次）= 默认 10 次 LLM 调用。Mitigation：辩论默认 2 轮可配置；三角色独立分析可并行执行减少延迟。

**[R2] 侦察兵 AKShare 接口不稳定**：行业板块接口可能超时。Mitigation：侦察兵数据获取失败时 graceful fallback，只基于历史报告推荐，不阻塞整体流程。

**[R3] 持仓多时 prompt 过长**：30+ 只持仓的报告摘要可能超出 context window。Mitigation：按市值排序，详细分析前 20 只，其余合并汇总。

**[R4] Tier 1 报告格式不统一**：不同时期生成的报告字段可能有差异。Mitigation：读取报告时做容错处理，缺失字段用默认值填充。

**[R5] 组合建议可能与单标的分析矛盾**：Tier 2 可能建议减仓一只 Tier 1 评级为 Buy 的股票（因组合集中度原因）。这不是 bug，是设计——组合视角和单标的视角本就不同。在 AdviceItem 的 reasoning 中显式说明。
