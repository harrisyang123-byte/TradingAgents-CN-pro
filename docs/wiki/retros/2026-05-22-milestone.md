## W.W.L.D 分析

### 1. What Went Well (亮点)

- **规划驱动实施 (Planner -> Applier)**
  垂直切片 (Vertical Slicing) 原则在整个实现周期表现优异。`tasks.md` 的端到端划分 (如 `fund-tier1-analysis` 中的数据层 -> Graph -> SSE -> API -> Frontend) 确保了每个任务都是可独立验证的。
- **架构复用与隔离 (Architecture & Adapter Pattern)**
  LangGraph 的核心状态机和 `DebateState` 在单只股票、投资组合 (Portfolio Advisor) 和基金 (Fund Analysis) 三个场景中得到了完美复用。采用适配器模式 (Adapter Pattern) 和新建独立 Graph (如 `fund_graph.py`) 的策略，成功实现了功能的非破坏性扩展，避免了回归问题。
- **状态无状态化管理**
  在 `portfolio-advisor` 中，通过 `portfolio_context` 字符串直接将上下文注入 Prompt，保持了 LangGraph 引擎的无状态化，避免了和全局数据库的强耦合。

### 2. What Went Wrong (问题)

- **外部依赖的脆弱性**
  这是最大的痛点。在 `upstream-alignment` 和 `fund-tier1-analysis` 中，AKShare/EastMoney 的 API 极不稳定，网络断开和数据缺失（如 QDII 基金无重仓股）频繁阻断端到端测试。不得不在代码中引入 `_RetryAKShare` 等补丁，增加了数据层的杂音。
- **过度工程与上游漂移**
  初期积累了大量架构债务。例如 `agent_utils.py` 膨胀到近 1400 行，引入了过度的防御性编程（防死循环、Qwen 专属补丁、ChromaDB 强依赖等）。这导致了长达一周的 `upstream-alignment` 阵痛期，才将代码恢复到干净的基线。

### 3. Lessons Learned (经验)

- **Adapter 模式优于重复造轮子**
  当引入新数据源或模型时，不应修改原有核心代码。`route_to_vendor()` 模式被证明处理多市场数据（A 股/港股/美股）比单一巨型工具函数更健壮。
- **降级和结构化 fallback 的重要性**
  针对不稳定的 LLM 输出和网络错误，标准化的异常捕获和降级提取（如今天在 `simple_analysis_service.py` 中增加的从 `detailed_analysis` 中提取报告）比试图通过复杂 Prompt 纠正 LLM 的临时性错误更有效。
- **不要把 Guardrails 变成技术债**
  针对特定弱模型（如 Qwen）的 hardcode 补丁，在切换到先进模型（DeepSeek/Claude）后反而成为了负担。系统的防御机制应该建立在通用层，而不是模型层。

### 4. Decisions to Make (待决策改进)

- [ ] **外部 API 降级与缓存策略**：考虑引入持久化层（或 Redis 更强缓存）作为 AKShare 故障时的 Backup，确保系统 E2E 可测试性不受外部网络影响。
- [ ] **E2E 测试 Mock 机制**：建立一套完善的针对第三方数据供应商（AKShare）的 Mock 系统，不再依赖实时网络完成端到端验证。
- [ ] **后续方向聚焦**：Tier 1（基金/股票）和 Tier 2（持仓）基础已经打通，接下来的重点应放在 `p3-long-tail` 遗留项或智能定投/回测能力的探索。
