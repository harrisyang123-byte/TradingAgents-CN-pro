# 需求文档 — v4：分层独立深度投研系统

## 功能概述

把现有 v3「一次 `run.sh all` 跑完 Step 0-7 的单链路全量分析」彻底重构为**模拟真实投研机构的分层、解耦、常驻式深度分析体系**：以「最大化用户长期复利、不错失机会」为公司总目标，按「七大类资产 → 大类内行业 → 行业内个股」三层逐级深入，每一层都是一个独立的「分析部门」，由对立角色经多轮辩论、再由部门总监拍板。每个分析单元（某大类 / 某行业 / 某个股）**独立可触发、独立缓存、独立有新鲜度**，不再一次性全量跑完；层与层之间通过「上游快照指纹 + stale 软提醒」保持约束链一致性而不强制刷新。系统同时支持**本地运行**与 **AI 代跑**两种模式，代跑产物覆盖式落盘且本地拉取后前端能正确解析展示。

> 边界声明：v4 是大范围重构（9 条功能需求，超出单 Feature 推荐上限），故执行模式为 staged 分段交付。本需求文档定义 v4 的**完整目标范围**，实现时按「资产层 → 触发/约束机制 → 权益深链 → 非权益方案 → 前端/双跑」的优先级分阶段落地，每阶段独立可用、可回归。

## 用户故事

- 作为**个人投资者（本地运行者）**，我希望系统像一家真正的投研公司那样，先把每一类资产的形势研究透、再给配比，然后逐层深入到行业和个股，以便我敢于依据它的结论实际调仓，而不是面对一份浅尝辄止的全量报告不敢用。
- 作为**个人投资者**，我希望能自己选择「先深度分析哪些资产/行业」（系统也能基于风口与长期投资理论推荐），按需触发深跑而非每次烧钱全量跑，以便控制成本和等待时间。
- 作为**委托 AI 代跑的用户**，我希望只把本地持仓交给 AI，AI 跑完的全部分析结论被覆盖式存盘、我拉代码下来后前端能原样解析展示，以便本地与代跑两种方式得到一致的体验。
- 作为**使用者**，我希望任何一层的结论都清楚标注「基于哪一版上游、是否已过时」，当上游变化时给我软提醒而不是强制重算，以便我在一致性与灵活性之间自己拿捏。

## 功能需求

### FR-001: 七大类资产体系定义与持仓穿透归类
- **类型**: 功能需求
- **优先级**: P0
- **描述**: When 系统初始化资产体系或导入用户持仓时, the system shall 按固定的七大类资产框架对全部持仓做穿透式归类，并标注每类的「可下钻深度」。
- **七大类资产（v4 基座，固定）**:

  | 序号 | 大类资产 | 包含内容举例 | 最深下钻层级 |
  |------|----------|--------------|--------------|
  | 1 | 权益 | A股/港股/美股个股、股票型基金、ETF | 大类 → 行业 → 个股（三层） |
  | 2 | 固定收益 | 国债、地方债、企业债、可转债、债券基金 | 大类 → 品种/久期结构（两层） |
  | 3 | 现金及等价物 | 活期存款、货币基金、短期国债、逆回购（各国货币归此类） | 大类 → 持有结构（两层，持有型） |
  | 4 | 大宗商品 | 能源（原油/天然气）、工业金属（铜/铝）、农产品（大豆/玉米） | 大类 → 品种/工具（两层） |
  | 5 | 贵金属 | 黄金、白银、铂金等（独立于大宗商品） | 大类 → 品种/工具（两层） |
  | 6 | 房地产 | REITs、实物房产、房地产私募基金 | 大类 → 工具（REITs 可下钻，实物房产仅记敞口） |
  | 7 | 另类投资 | 虚拟币（比特币、以太坊等）及其他另类 | 大类 → 品种（两层） |

- **验收标准**:
  - [ ] AC1.1: WHEN 导入持仓 THE SYSTEM SHALL 将每一笔持仓（含基金按底层资产穿透）归入上述七大类之一，无法归类的标记为「待人工归类」而非静默丢弃。
  - [ ] AC1.2: THE SYSTEM SHALL 区分每类资产的「可交易标的」与「持有型敞口」——可交易（如 ETF/REITs/债基/金条 ETF）支持下钻到品种/标的；持有型（实物房产、实物贵金属、各国现金）仅作为配置桶记录敞口，不推荐具体标的。
  - [ ] AC1.3: THE SYSTEM SHALL 为每个大类记录其「最深下钻层级」，前端据此决定该大类详情页展示「行业+个股」还是「持有结构方案」。
  - [ ] AC1.4: IF 用户持仓为空（仅 AI 代跑给定持仓） THEN 系统按传入的持仓文件做同样的穿透归类。

### FR-002: 大类资产逐类深度分析部门（多角色 3 轮辩论 + 总监拍板）
- **类型**: 功能需求
- **优先级**: P0
- **描述**: When 用户触发对某一大类的深度分析时, the system shall 以一个独立「大类研究部门」对**该单一大类**完成多维度尽调与 3 轮对立辩论，产出该大类的形势研判与发展方向报告，而非一次会议同时讨论所有大类。
- **验收标准**:
  - [ ] AC2.1: THE SYSTEM SHALL 对单个大类独立运行分析部门，输入覆盖该资产相关的多维信息：宏观（利率/通胀/货币政策/经济周期）、微观/基本面（该资产估值与供需）、舆情与资金面、政策与地缘政治。
  - [ ] AC2.2: THE SYSTEM SHALL 配置参考真实投研机构的对立角色（如「多头研究员 vs 空头研究员」+ 专项视角分析师），并进行**固定 3 轮**辩论，每轮记录双方论点与反驳。
  - [ ] AC2.3: WHEN 3 轮辩论结束 THE SYSTEM SHALL 由「大类部门总监」角色拍板，输出该大类的：当前形势研判、发展方向（看多/看空/中性 + 理由）、主要风险、建议趋势。
  - [ ] AC2.4: THE SYSTEM SHALL 把每个大类的分析报告独立落盘、独立标注更新时间与新鲜度，七大类各自有独立的分析记录，互不覆盖。
  - [ ] AC2.5: IF 某大类用户当前零持仓 THEN 仍允许对其触发分析（用于发现机会/择机配置），不因无持仓而跳过。

### FR-003: 资产配比决策与约束下传（配置委员会总监拍板）
- **类型**: 功能需求
- **优先级**: P0
- **描述**: When 各大类的独立分析已就绪、用户触发资产配比决策时, the system shall 在已澄清的各大类形势之上，由资产配置总监综合产出七大类目标配比报告，并将权益额度等约束向下传递给行业层。
- **验收标准**:
  - [ ] AC3.1: WHEN 触发资产配比 THE SYSTEM SHALL 读取七大类各自最新的分析结论作为输入；IF 某大类尚无分析或其分析已 stale THEN 在配比报告中显式标注「该类输入缺失/过时」并允许用户选择先补跑或带风险继续。
  - [ ] AC3.2: THE SYSTEM SHALL 产出「当前配比 → 目标配比」对照，七大类目标配比之和等于 100%，并给出每类调整方向与理由。
  - [ ] AC3.3: IF 用户/总监判断短期不配置某大类 THEN 允许该大类目标配比为 0%（主动放弃/暂不配置），系统须视 0% 为合法决策而非缺失，并记录「主动归零」的理由；其余大类配比之和仍须等于 100%。
  - [ ] AC3.4: THE SYSTEM SHALL 将权益目标配比作为约束（权益额度）向下传递，成为权益大类内行业层的总权重上限；IF 权益目标配比为 0% THEN 不触发权益深链（行业/个股层），并在前端标注「本期不配置权益」。
  - [ ] AC3.5: THE SYSTEM SHALL 为配比报告记录其依据的「各大类分析快照指纹」，供下游一致性校验与软提醒使用（见 FR-005）。

### FR-004: 分层独立分析的触发机制与新鲜度状态机
- **类型**: 功能需求
- **优先级**: P0
- **描述**: When 任意分析单元（大类 / 行业 / 个股 / 资产配比）需要运行时, the system shall 以「按单元独立触发 + 统一新鲜度状态机」的机制驱动，放弃一次性全量跑完；**触发的主入口是 CLI 对话方式**（由本地用户或 AI 在本地调起 agent 跑），前端仅负责展示单元状态与软提醒、不直接接 API 调起 LLM 分析。
- **触发方式定位（重要修正）**: 分析过程是 claude/AI 在本地调子 Agent 跑的重计算，不走「页面点击 → 后端 API → LLM」的在线链路。因此：
  - **主入口 = CLI 对话**：用户用自然语言对 AI 说「分析权益大类」「深辩 AI 行业」「刷新现金配比」等，由 AI 解析为对应单元的触发命令并在本地执行、覆盖式落盘。
  - **前端 = 只读状态视图**：前端展示每个单元的新鲜度颜色、更新时间、stale 软提醒与「建议在 CLI 中运行的指令提示」，但不承担「点一下就跑 LLM」的职责（避免长任务、鉴权、成本问题压到 Web 层）。

- **设计说明（易懂的触发机制）**: 每个分析单元是一张「研究卡片」，卡片有统一的颜色状态语言，用户一眼看懂该不该跑（并据此到 CLI 触发）：

  | 状态 | 颜色 | 含义 | 用户动作 |
  |------|------|------|----------|
  | 未分析 | 灰 | 从未跑过 | 在 CLI 对话中说「分析<单元>」按需深跑 |
  | 分析中 | 蓝（转圈） | 正在跑 | 等待 |
  | 新鲜 | 绿 | 在有效期内且上游未变 | 可直接采信 |
  | 建议刷新 | 黄 | 超过有效期，或上游已更新（软提醒） | 在 CLI 中「刷新<单元>」，也可继续用旧的 |
  | 失败 | 红 | 上次运行失败 | 查看原因并在 CLI 重试 |

- **验收标准**:
  - [ ] AC4.1: THE SYSTEM SHALL 以 CLI 对话为主触发入口：用户用自然语言指定要分析/刷新的单元（大类/资产配比/行业/个股），AI 解析为单元级触发命令并在本地执行；同时保留等价的脚本命令（如 `run.sh` 子命令）供本地用户直接调用。
  - [ ] AC4.2: THE SYSTEM SHALL 支持上游更新引发的下游级联**软提醒**（仅置黄、不自动跑，见 FR-005）；定时/后台扫描过期单元为可选能力，扫描到过期仅置黄提醒，不强制自动深跑。
  - [ ] AC4.3: THE SYSTEM SHALL 为每类分析单元配置独立的时间有效期（TTL），不同层级可不同（如大类配置、行业、个股各自一档 TTL），TTL 可配置。
  - [ ] AC4.4: WHEN 触发某单元 THE SYSTEM SHALL 仅运行该单元（及其明确选择的范围），不连带强制重跑其它单元；多个单元可分别独立处于不同状态。
  - [ ] AC4.5: THE SYSTEM SHALL 对每个单元落盘记录：状态、最近运行时间、TTL、所依据的上游快照指纹、运行结果产物路径。
  - [ ] AC4.6: THE SYSTEM SHALL 在前端为每个单元提供「该如何在 CLI 中触发」的可读指令提示（如展示对应自然语言说法或脚本命令），而非提供直接调起 LLM 的按钮。
  - [ ] AC4.7: IF 一个单元正在分析中 THEN 重复触发该单元应被去重或排队，不产生并发重复运行。

### FR-005: 约束链一致性校验与 stale 软提醒（不强制刷新）
- **类型**: 功能需求
- **优先级**: P0
- **描述**: When 任一上游单元（宏观/资产配比/行业配比）更新后, the system shall 通过「上游快照指纹」识别出依赖它的下游单元并标记为 stale，以软提醒形式显式告知用户，但不强制重算、不阻断使用旧结论。
- **验收标准**:
  - [ ] AC5.1: THE SYSTEM SHALL 在每个下游单元产物中记录其依据的上游单元版本/指纹（如「本行业配比基于资产配比 v3、宏观 v7」）。
  - [ ] AC5.2: WHEN 某上游单元产生新版本 THE SYSTEM SHALL 将所有引用其旧版本的下游单元置为「建议刷新（黄）」，并在前端展示可读提示，如「行业配比基于 3 天前的资产配置，建议刷新」。
  - [ ] AC5.3: THE SYSTEM SHALL NOT 在上游变化时自动重跑下游，也不阻止用户继续查看/采用 stale 结论（软提醒，非硬阻断）。
  - [ ] AC5.4: WHEN 用户主动刷新某下游单元 THE SYSTEM SHALL 使其重新绑定到当前最新上游指纹，并将状态恢复为「新鲜（绿）」。
  - [ ] AC5.5: THE SYSTEM SHALL 在资产配比与下层使用约束（如权益额度下传行业层）时校验链路完整性，发现下游使用的约束来自已过时上游时，仅报警提示而不修正数值。

### FR-006: 权益大类深链——行业深辩 → 行业间配比 →（独立部门）个股分析 → 行业内资金配比
- **类型**: 功能需求
- **优先级**: P0
- **描述**: When 用户进入权益大类详情并触发分析时, the system shall 在权益额度约束内，按「先把行业研究透、再据此配比」的正确顺序展开：先对候选行业做**逐个独立深度分析（多轮辩论定方向）**，基于深度结论做**行业间资金配比**（行业层到此完成）；随后由一个**独立的行业内研究部门**对行业内公司/资产做详细分析（个股独立分析），最后完成**行业内资金配比**。行业选择支持内置推荐与用户对话式挑选。
- **验收标准**:
  - [ ] AC6.1: THE SYSTEM SHALL 内置若干候选行业（依据风口与长期投资理论），并在 CLI 对话中询问用户「先深度分析哪些行业」，用户可自选、可采纳系统推荐。
  - [ ] AC6.2: WHEN 用户触发某单一行业的深度分析 THE SYSTEM SHALL 以独立「行业研究部门」对该行业做多轮对立辩论（参考行业研究最佳实践配置角色），产出行业方向研判（景气、空间、风险、配置建议）——**此步先于行业间配比**。
  - [ ] AC6.3: WHEN 已选行业的深度分析就绪 THE SYSTEM SHALL 由行业配置团队基于各行业的深度分析结论，在权益额度上限内产出行业间资金配比（各行业目标权重之和 ≤ 权益额度）；至此行业层完成。IF 某行业深度分析缺失/stale THEN 在配比中显式标注并允许先补跑或带风险继续。
  - [ ] AC6.4: WHEN 行业方向与行业权重确定后触发个股 THE SYSTEM SHALL 由一个**独立的「行业内研究部门」**对该行业内的公司/资产做详细分析，在该行业内找候选标的，并对**每只个股独立运行一次分析**（个股分析互相独立、独立缓存），产出评级与目标价。
  - [ ] AC6.5: WHEN 个股分析就绪 THE SYSTEM SHALL 在该行业目标权重内对选定个股做行业内资金配比，产出每只个股的目标权重与买入区间。
  - [ ] AC6.6: THE SYSTEM SHALL 使行业层、个股层各自遵守 FR-004 的独立触发与 FR-005 的快照指纹/软提醒机制（行业深辩变 → 行业配比置黄；行业配比变 → 个股配比置黄）。

### FR-007: 非权益六大类的差异化投资方案
- **类型**: 功能需求
- **优先级**: P1
- **描述**: When 用户进入某个非权益大类（固定收益/现金及等价物/大宗商品/贵金属/房地产/另类投资）详情并触发分析时, the system shall 按该资产本质给出与其下钻深度匹配的投资方案，而非套用权益的「行业→个股」结构。
- **验收标准**:
  - [ ] AC7.1: THE SYSTEM SHALL 对每个非权益大类运行其专属的分析部门（多轮辩论 + 总监拍板，复用 FR-002 的部门范式），输出该类的方向研判与投资方案。
  - [ ] AC7.2: 现金及等价物 —— THE SYSTEM SHALL 产出「持有结构方案」，在活期/货币基金/短期国债/逆回购等工具间给出建议分布与理由（持有型，不推荐个券）。
  - [ ] AC7.3: 固定收益 —— THE SYSTEM SHALL 产出久期与品种结构建议（如国债/信用债/可转债/债基的配比与久期取向），结合利率环境。
  - [ ] AC7.4: 大宗商品、贵金属 —— THE SYSTEM SHALL 产出品种/工具层方案（如贵金属在实物/黄金 ETF/金矿股间的取向；大宗在能源/工业金属/农产品间的取向），可交易工具可下钻，纯持有型仅记敞口。
  - [ ] AC7.5: 房地产 —— THE SYSTEM SHALL 对可交易的 REITs 下钻到工具层方案，对实物房产仅作为配置桶记录敞口、给出宏观层面持有建议。
  - [ ] AC7.6: 另类投资 —— THE SYSTEM SHALL 对虚拟币等给出品种层方案与风险提示（高波动/合规风险显著标注）。
  - [ ] AC7.7: THE SYSTEM SHALL 使所有非权益大类方案同样遵守 FR-004 独立触发与 FR-005 快照指纹/软提醒机制。

### FR-008: 三层 Tab 前端结构
- **类型**: 功能需求
- **优先级**: P0
- **描述**: When 用户访问组合总揽时, the system shall 以三层 Tab 结构呈现「资产配置 → 大类详情 → 行业/个股」，并在每个分析单元上展示 FR-004 的新鲜度状态与 FR-005 的软提醒。
- **三层结构**:
  ```
  组合总揽（顶部 Tab 栏）
  ├── Tab 1：资产配置        七大类独立分析报告卡片 + 总监配比报告（当前→目标）
  ├── Tab 2：大类详情(动态)   点进某大类：权益→行业配比+各行业卡片；非权益→该类投资方案
  └── Tab 3：行业/个股(动态)  点进某行业：行业深辩报告 + 行业内个股分析 + 行业内资金配比
  ```
- **卡片 vs 表格使用原则（用户偏好）**: 数量少、需突出摘要与状态的用**卡片**；数量多、需横向对比的用**表格**。具体：
  - Tab 1 七大类（仅 7 个）→ **卡片**（每类一张，突出状态色 + 摘要 + 当前→目标配比）。
  - Tab 2 权益行业列表、Tab 3 个股列表（数量多、需对比权重/评级/景气）→ **表格**（列含名称、状态、目标权重、关键指标、更新时间、上游 stale 标记）。
  - 非权益大类的投资方案（条目少）→ 卡片或小表按信息量择优。
- **验收标准**:
  - [ ] AC8.1: THE SYSTEM SHALL 在 Tab 1 以**卡片**展示七大类，每卡显示该类分析摘要、状态颜色（灰/蓝/绿/黄/红）、最近更新时间，以及「当前→目标」配比。
  - [ ] AC8.2: WHEN 用户点击某大类 THE SYSTEM SHALL 进入 Tab 2 大类详情：权益以**表格**展示行业列表（含行业间配比、状态、关键指标）；非权益展示其差异化投资方案（FR-007）。
  - [ ] AC8.3: WHEN 用户点击某行业 THE SYSTEM SHALL 进入 Tab 3：展示行业深辩报告，并以**表格**展示行业内个股分析列表与行业内资金配比（个股、评级、目标价、目标权重、状态）。
  - [ ] AC8.4: THE SYSTEM SHALL 在任意单元卡片/表格行上展示状态颜色，并在 stale 时显示可读软提醒文案（如「基于 N 天前的上游配置，建议在 CLI 中刷新」）及对应的 CLI 触发指令提示（不提供直接调起 LLM 的按钮，见 FR-004）。
  - [ ] AC8.5: THE SYSTEM SHALL 在缺少数据（未分析/未触发）时显示空态与引导（提示在 CLI 如何触发），而非报错或空白。

### FR-009: 双跑模式与产物覆盖式落盘解析
- **类型**: 功能需求
- **优先级**: P0
- **描述**: When 分析由本地用户运行或由 AI 代跑时, the system shall 使两种模式产出结构一致的产物并覆盖式落盘，AI 代跑产物以 **git 友好的结构化文件**随仓库传输，用户本地拉取后通过**幂等解析/导入机制写入数据库**，前端读数据库（或静态快照）正确解析展示，无需区分产物来源。
- **落盘与传输方案（用户要求想清楚）**:
  - **运行态存储 = 数据库**：分析结论最终落 MongoDB，供前端 API 读取与查询。
  - **git 传输载体 = 单元粒度的结构化 JSON 文件**（非数据库 dump、非二进制）。每个分析单元（某大类/某行业/某个股/配比）一个稳定路径的 JSON（如 `data/v4/<层>/<单元id>.json`），文件 diff 友好、可人读、可 code review，AI 代跑后 commit 的就是这些文件。
  - **产物 → 数据库 = 幂等导入脚本**：本地 `git pull` 拿到 JSON 后，运行导入命令按「单元唯一键 upsert」写入 MongoDB（同单元覆盖更新、不动其它单元）；前端始终读数据库。亦保留 v3 的「静态快照 fetch」作为无后端降级展示路径。
- **验收标准**:
  - [ ] AC9.1: THE SYSTEM SHALL 支持两种运行入口：① 本地运行（连本地数据/数据库）；② AI 代跑（仅接收用户提供的持仓文件，不依赖用户本地数据库）。
  - [ ] AC9.2: THE SYSTEM SHALL 使两种模式产出**结构同构**的落盘产物（同一套 schema 的分析报告/配比/状态/快照指纹），前端解析逻辑对两者一致。
  - [ ] AC9.3: THE SYSTEM SHALL 以**单元粒度的结构化 JSON 文件**作为 git 传输载体（每单元一个稳定路径文件，diff 友好、可人读），AI 代跑产物即这些文件，避免传输数据库 dump 或二进制。
  - [ ] AC9.4: WHEN 某单元被重新分析 THE SYSTEM SHALL 以覆盖式更新该单元的 JSON 文件（保留单元粒度，不整体重写其它单元），并更新其状态与时间戳。
  - [ ] AC9.5: WHEN 用户本地拉取产物 THE SYSTEM SHALL 提供**幂等的解析/导入机制**（按单元唯一键 upsert 入 MongoDB，重复导入不产生重复或脏数据），导入后前端按三层 Tab 正确展示，效果与本地运行一致。
  - [ ] AC9.6: THE SYSTEM SHALL 确保落盘产物中的敏感财务数据（持仓/处方）遵循现有 .gitignore 与隐私约定；若产物文件含敏感数据需共享，须走私有仓库。

## 技术约束

- **沿用现有技术栈**：后端 FastAPI 0.115+ / Uvicorn，前端 Vue 3.5+ + Vite + Element Plus，存储 MongoDB + Redis，LLM 决策通过 `.md` 子 Agent 定义 + Workflow 编排（claude -p 驱动），不在 Python 内直接 `llm.invoke()`（延续 v3 设计铁律）。
- **数据源沿用**：AKShare / Tushare / BaoStock（A股）、yfinance / Finnhub（港股/美股）；新增的非权益大类（固收/大宗/贵金属/房地产/另类）数据源在 design 阶段评估补强，缺失数据源的大类先做「仅 LLM 知识 + 可得行情」的降级分析并显式标注。
- **市场覆盖延续 v3 边界**：权益行业深辩与个股推荐主力为 A 股；港股/美股个股走独立深度分析链路；大类资产层可纳入海外/全球敞口。v4 不扩大市场覆盖范围，重点在分层深度与机制。
- **分析单元化**：每个分析单元（大类/行业/个股/配比）需有稳定唯一标识与独立产物文件，落盘 schema 须同时满足本地运行与 AI 代跑两条路径（FR-009）。
- **触发链路分离**：重计算（LLM 子 Agent 深跑）只在 CLI/本地由 claude 调起，不经 Web 在线接口触发；前端只读状态与产物。后端可提供「读取产物 / 查询状态 / 接收导入」类接口，但不承载在线 LLM 长任务。
- **落盘与传输**：运行态存 MongoDB；git 传输载体为单元粒度结构化 JSON 文件（diff 友好、可人读）；本地拉取后用幂等导入脚本按单元唯一键 upsert 入库；保留静态快照 fetch 作为无后端降级路径。
- **快照指纹机制**：上游产物版本/指纹需可被下游引用与比对，作为 stale 判定依据（FR-005）；不得用「时间先后」近似替代指纹比对。
- **成本与时长**：放弃一键全量；单元级触发须可中断、可单独重试，失败单元不污染其它单元状态。
- **目录与隐私**：落盘沿用 `data/`（已在 .gitignore），静态快照若共享须走私有仓库；不得硬编码密钥或敏感信息。
- **兼容/迁移**：v4 与 v3 的关系（替换或并存、历史 `portfolio_advice` 数据迁移与否）在 design 阶段决策，本需求不预设删除 v3 资产。

## API 依赖

项目大类为 existing 全栈应用，已有后端 API 与前端。v4 在现有 `app/routers/` 基础上扩展，建议 API 策略：

- **触发类（CLI 为主）**：单元级深跑由 CLI 对话/脚本（如 `run.sh` 子命令）在本地调起，**不经 Web 在线 LLM 接口**。后端仅需提供「产物导入 / 状态写入」类接口或由导入脚本直写库；前端不提供「点击即跑 LLM」的按钮。
- **读取类**：提供三层 Tab 所需的读取接口——七大类配置与状态、单大类详情（含行业配比或非权益方案）、单行业详情（深辩+个股+资金配比），每个响应须带单元状态、更新时间、上游快照指纹/stale 标记。
- **状态/新鲜度**：提供查询各单元新鲜度状态机的接口（灰/蓝/绿/黄/红 + TTL + stale 原因）。
- **双跑产物**：AI 代跑与本地运行写同构 schema，前端通过统一解析层读取（在线 API 或静态快照 fetch 两种来源）。
- 现有相关接口（`/api/portfolio/overview`、`/analysis/plan`、`/analysis/execute`、`/analysis/{task}/status`、行业 refresh、watchlist 等）作为改造基线，design 阶段评估复用/重构。
- 完整 API 文档参照运行时 `http://localhost:8000/docs`。

## 非功能需求

### NFR-001: 性能与成本
- AC1.1: 单个分析单元（一个大类/一个行业/一只个股）的一次深跑应可独立完成并落盘，不要求全量串跑；系统不得因某单元运行而阻塞用户查看其它单元的已有结论。
- AC1.2: 读取类接口（三层 Tab 展示）在使用缓存产物时应秒级响应，不触发实时 LLM 调用。

### NFR-002: 一致性与可追溯
- AC2.1: 每个产物须可追溯其依据的上游版本（快照指纹）与生成时间；任意下游结论都能回答「我基于哪一版上游」。
- AC2.2: 约束链校验发现下游使用过时上游约束时，必须可见地软提醒（不静默、不强制修正）。

### NFR-003: 可用性与可见性
- AC3.1: 任意单元的状态（未分析/分析中/新鲜/建议刷新/失败）必须在前端以统一颜色语言一目了然。
- AC3.2: 运行失败、数据降级（如某数据源缺失）必须显式提示并可定位原因，延续 v3「保证看得见」（run_report）的理念。

### NFR-004: 双跑一致性
- AC4.1: 同一份持仓输入，本地运行与 AI 代跑产出的产物 schema 必须一致，前端解析与展示结果在结构上对齐。
- AC4.2: 覆盖式落盘不得破坏未重跑单元的既有产物与状态。

### NFR-005: 安全与隐私
- AC5.1: 持仓/处方等敏感财务数据落盘须遵循 .gitignore 与私有仓库约定，不被意外公开。
- AC5.2: 不在代码或产物中硬编码任何 API key 或凭据。
